## Границы и ответственность

- Абулхаир создаёт редактируемый Figma: сначала дизайн, затем checkpoint реализации React.
- Артём владеет frontend и его тестами; Нурсултан не меняет эти файлы параллельно.
- Чингиз готовит синтетический набор `data/fixtures/synthetic/workspace/`: длинный диалог,
  более восьми критериев, контекст разных ролей, N/A, флаги и история решений.
- Нурсултан проверяет семантику дизайна и независимо проходит интерфейс после checkpoint.
  Provider, scoring и API не изменяются без подтверждённого дефекта и согласования владельца.
- В Figma, скриншотах и публичных фикстурах используются только собственные синтетические
  данные. Они не являются человеческим Ground Truth или доказательством точности AI.
- Живые OpenAI-вызовы запрещены текущим поручением. Ключи и локальный `.env` не читаются.
  Реальный API проверяется без ключа либо через явно внедрённые синтетические ответы.
- Браузерная проверка относится к обычному React-приложению по HTTP. Ранее заблокированный
  `file://` и обходы этого ограничения не используются.

## Проверяемые смысловые различия

| ID | Сценарий | Критерий приёмки |
| --- | --- | --- |
| W-01 | Выбор критерия | Выбранная строка имеет нейтральный фон/контур. Зелёный выделяет linked evidence, teal со статусной иконкой/словом обозначает pass. Фокус клавиатуры различим отдельно в обеих темах. |
| W-02 | Переход к доказательству | Сохраняются диалог, evaluation, версии транскрипта и чек-листа. Подсвечены существующие ID и включительный диапазон; прокручивается нужная панель, положение очереди не сбрасывается. |
| W-03 | Контекст и пропуск | Доказательство может указывать на client/bot/system как контекст действий оператора. Если контекст скрыт фильтром, переход к evidence раскрывает нужный фрагмент либо явно предлагает его показать. Для пропуска виден проверенный диапазон и ожидаемое действие; цитаты берутся из связанного снимка. |
| W-04 | Ответы и итог | «Нет», N/A, не оценено, ошибка и null-итог отличаются текстом. N/A исключает вес; исходный и эффективный веса не смешаны. Ноль применимых весов показан с причиной, а не как 0/100. |
| W-05 | Грубое нарушение | `gross_errors` отображается отдельным флагом и не обнуляет балл. Пользовательские флаги остаются самостоятельными критериями; отсутствие `gross_errors` не означает доказанное отсутствие нарушений. |
| W-06 | AI и проверяющий | Исходный и финальный итоги находятся рядом и подписаны. Оценка AI, комментарий к апелляции и решение проверяющего не смешаны. Видны версия/ревизия и причина решения. |
| W-07 | История решений | После нескольких решений первоначальная оценка и ранее принятые значения остаются прежними. Старое решение отображает сохранённый `decision.result`, а не позднее `current`. Confirm также сохраняется в истории. |
| W-08 | Пользовательский чек-лист | Число критериев берётся из версии: проверяется 12 строк и больше. Названия, шкалы, флаги и разрешённый N/A не завязаны на восемь seed ID. Последние строки доступны с клавиатуры и через внутреннюю прокрутку. |
| W-09 | Асинхронность и повтор | Loading/queued/running/failed/error различимы. Без ключа появляется AI_NOT_CONFIGURED, не готовая оценка. Повтор — явное действие; поздний ответ другого диалога не подменяет текущий снимок. |
| W-10 | Черновик апелляции | Несохранённый комментарий/решение не исчезает молча при выборе другого критерия, диалога или представления и не переносится под чужой criterion/snapshot. Черновик сохраняется с правильной привязкой либо переход требует явного решения пользователя. Принятое сохранение и ожидающая отправка различимы; конфликт ревизии не выдаётся за успех. |
| W-11 | Длинный workspace | Не менее 120 сообщений, длинные слова и RU/KZ/EN не делают элементы недоступными. Desktop-панели имеют ограниченную высоту и внутренний scroll; evidence в начале/середине/конце достижимо. |
| W-12 | Темы, размер, клавиатура | Light/dark показывают одинаковый смысл. Проверяются desktop и узкий экран, изменение ширины, Tab/Shift+Tab/Enter/Escape, возврат фокуса после диалога/панели и отсутствие клавиатурной ловушки. Узкий layout не скрывает transcript, scorecard или историю без способа открыть их. |

Статус pass не передаётся одним цветом. Грубое нарушение, низкая оценка и требование
ручной проверки также имеют понятные подписи. Цвет evidence означает связь с сообщением,
а не правильность вывода модели.

## React checkpoint и воспроизводимость

Перед прогоном записываются commit SHA, HTTP URL, способ подачи синтетических данных и
фактический размер viewport. Для проверки безопасных ошибок запрещено вводить настоящий
ключ или URL организаторов. Управляемые ответы Playwright имеют явное синтетическое
происхождение; отдельный отказ без ключа проверяет настоящий API-путь.

Базовые команды уже существуют, но запись команды здесь не означает её выполнения:

```bash
cd frontend
npm run check
npm run test
npm run build
npm run test:e2e
```

Артём согласует, какие тесты покрывают новый workspace и откуда берётся текущий mock API.
Нурсултан использует отдельную вкладку обычного HTTP-приложения, чтобы не менять состояние
коллег. Браузерные доказательства сохраняются в игнорируемом `artifacts/` либо в каталоге
артефактов Codex; скриншот содержит только синтетические данные. В tracked-файл попадают
относительный сценарий, наблюдение и доступный путь к скриншоту, без сырых console payload.

Для ошибки проверяются видимое безопасное сообщение, возможность повтора и консоль:
допустимы фиксированные событие/статус/код, недопустимы transcript, prompt, полный API
ответ, `Error`/`Response`, ключи и исходные URL. Неожиданный сбой передаётся владельцу с
точными шагами, ожидаемым/фактическим результатом и версией; исправления проходят повторно
только затронутые сценарии.
