Нельзя заменять работу над точностью дополнительными функциями. Точная официальная формула сравнения с Ground Truth неизвестна.

## 5. Практика работы с Git

1. Участник клонирует репозиторий в свой каталог, делает `git fetch origin` и переключается на свою ветку.
2. До начала новой задачи синхронизирует свою ветку с актуальной `origin/main` обычным merge, сохраняя собственные изменения.
3. Работает небольшими коммитами в своей ветке и обновляет соответствующие строки роадмапа.
4. Отправляет ветку и PR в `main`. В описании: ID задач, результат, проверки, изменения контрактов/плана и ограничения.
5. Для каждого PR любого участника обязательна Q-01: отдельный агент `gpt-6.1-sol` / `xhigh`, проверка ошибок, логов и лишнего кода, исправления и повторный просмотр финального коммита по [CODE_REVIEW.md](CODE_REVIEW.md). Это относится и к документации/конфигурации. Создать PR можно до ревью; сливать до завершения проверки нельзя.
6. Абулхаир как интегратор объединяет совместимые изменения после проверок, сверяет отчёт Q-01, head SHA и CI. Другие участники получают обновлённый `main`. Отчёт другого PR или прежний статус DONE не заменяют текущую проверку.

Первичная база всех веток — коммит планирования. Создание ветки не означает назначения GitHub-прав конкретному аккаунту: доступы участников настраиваются отдельно, если их ещё нет. Имена аккаунтов Чингиза, Нурсултана и Артёма в текущем задании не переданы.

## 6. Как изменять план

При каждом изменении:

1. Описать обнаруженный факт, а не только предпочтение.
2. Исправить или добавить задачу своего участника с новым ID (`A-06`, `C-06`, `N-06`, `R-06` и далее).
3. Указать приоритет, зависимости, владельца и проверяемый результат.
4. Если меняется архитектура/API/арифметика — обновить соответствующий документ и `DECISIONS.md` в том же PR.
5. Добавить запись в журнал ниже. При конфликте сохранения плана объединить полезные изменения обеих сторон; статус подтверждается кодом/проверкой, а не более поздним временем редактирования.

Это требование распространяется и на последующие AI, которым участники передадут репозиторий. Роадмап можно уточнять автономно в пределах порученной задачи; нельзя молча расширять продукт или выдавать новую идею за правило организаторов.
