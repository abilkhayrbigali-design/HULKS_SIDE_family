## Что подтверждает новый сквозной тест

Браузер импортирует три новых синтетических RU/KZ/EN диалога, выбирает v1 и
запускает worker. Проверяются существующие доказательства и переход к полному
диапазону. Включены client/operator/bot/system и инструкция внутри клиентской
реплики: адаптер передаёт их как данные одного user-input, системные инструкции
аудитора остаются неизменными. Это структурная проверка промпта, не доказательство
семантической устойчивости модели или правильной оценки только оператора.

Через UI изменяются название/инструкция/вес контакта, удаляется closing и
добавляется произвольный критерий. После сохранения v2 реальный SDK-запрос
содержит точный новый snapshot, без удалённого и с добавленным ID. Повторный
импорт меняет транскрипт, а новая оценка использует его новую версию.
Старый запуск продолжает открывать старые правила и четыре исходных сообщения.

Синтетический вектор v1: N/A у идентификации исключает вес 20; контакт false,
консультация 15/20, ведение 7/10, остальные балльные ответы true. Итог
`100 × (80 − 10 − 5 − 4.5) / 80 = 75.63`. Грубая ошибка true показана отдельно.
У v2 веса дают знаменатель 110 и итог 73.18; это проверка арифметики.
Override контакта даёт final 88.13 при original 75.63, затем confirm повышает
revision до 2. Оба решения сохраняются после reload, original и v1 не меняются;
число SDK-ответов при апелляциях не увеличивается. Эти заданные ответы
намеренно не являются содержательной оценкой синтетической переписки.

Существующие pytest дополнительно проверяют несуществующие/обратные evidence,
недопустимые шкалы и типы, нулевой знаменатель, Decimal/ROUND_HALF_UP,
конфликты revision, SQL-неизменяемость, rollback, рестарт worker, timeout/429/5xx,
ограниченный retry budget, сохранение known usage и безопасные caplog.
Benchmark реализован и проверен синтетическими тестами. В `data/private/`
основной и новой копий просмотрены только агрегированные признаки JSON:
16 файлов, 0 документов `annotation_source=human`, 0 человеческих кейсов.
Никаких метрик точности по ним не рассчитывалось.

## Изменения и диагностика

Подтверждённых новых ошибок production-кода на текущем main не обнаружено.
Q-01 выявил P2 в добавленном тестовом сервере: module-level app при импорте
успевал читать `.env` до явных изолированных настроек. Перед импортом app.main
теперь отключается env_file и без учёта регистра удаляются алиасы настроек только в отдельном
процессе harness. Subprocess-регрессия с запрещённым dotenv-reader и невалидными
настройками воспроизвела отказ до исправления и проходит после него.
Закрыт пробел проверки: редактирование критериев и апелляции теперь проходят
одним тестом через настоящий backend, а не только через mock API.
Проверка включена в CI full-application. README дополнен фактическим запуском;
команда копирования `.env` теперь сохраняет уже существующий файл.

Переиспользован подготовленный в рабочей ветке участника инструмент
`tools/check_public_readiness.py` с его пятью регрессиями; исходная ветка не
менялась. Это read-only эвристический аудит, а не сертификат отсутствия секретов.
Новых production-событий нет: используются `cqa.import/dataset_import_completed`,
`cqa.evaluation/ai_request_started|ai_request_completed|appeal_created`,
`cqa.worker/evaluation_started|evaluation_completed`,
`cqa.evaluation/appeal_decision_saved` и HTTP-сводки `cqa.requests`.
Новый аудит пишет `cqa.public_readiness/public_readiness_started|completed|failed`.
Его синтетическая регрессия удаляет подписанный URL из HEAD, но сохраняет его
в истории: ожидается WARNING/REVIEW_REQUIRED без вывода значения в report/caplog.
Сценарий реального backend проверяет отсутствие маркера транскрипта в console;
внешние API не вызывались. Ошибки selectors при создании нового теста исправлены
в самом тесте и не выдаются за дефекты приложения.

## Проверка перед публичностью

```bash
mkdir -p artifacts/submission
uv run --project backend --locked python tools/check_public_readiness.py \
  > artifacts/submission/public-readiness.json
```

Инструмент читает index и все коммиты, достижимые из **локальных refs**; не
открывает рабочий `.env`/приватные файлы, не меняет историю/remote/видимость.
Вывод — безопасные коды, санитизированные пути и количества, без совпавших
значений. Exit 0 означает отсутствие обнаруженных блокеров эвристики,
1 — требуется разбор, 2 — аудит не выполнен. Untracked-файлы и недостижимые
объекты не сканируются; бинарные/большие объекты явно отмечаются. Перед
публикацией надо обновить предназначенные к публикации remote refs и повторить
аудит; в этой сессии после fetch origin/main выполнен и git fetch origin для доступных
remote refs. Удалённые GitHub artifacts/PR и недостижимые объекты не охвачены.

Предварительный аудит до коммита охватил 163 коммита/609 уникальных blobs,
приватных путей и ключеподобных литералов не выявил; 5/5 gitignore probes PASS.
Три группы content findings разобраны: синтетическая подпись loopback IPv6
в `test_valid_http_settings_preserve_signed_url_and_support_ipv6`, и два
URL_PARSE_REVIEW в тестах отклонения невалидной конфигурации URL. Это тестовые
литералы/преднамеренно повреждённые URL, не найденные рабочие секреты.
Эвристика сохраняет REVIEW_REQUIRED; исключения, скрывающие такие проверки,
не добавлялись. Незакоммиченные tracked-изменения также давали ожидаемые
предупреждения; финальный аудит нужно выполнять на чистом index/дереве.

До открытия владелец должен проверить происхождение опубликованных данных,
все remote-ветки/теги и доступные GitHub artifacts/PR, которые этот локальный
сканер не проверяет. При подтверждённом секрете требуется его отзыв и отдельное
решение по истории; удаление только из HEAD недостаточно. Самостоятельно
переписывать историю или менять private на public в этой задаче нельзя.
