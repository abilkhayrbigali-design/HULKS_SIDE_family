# Логирование для всех участников и AI-агентов

Эти правила обязательны для новой реализации и доработок во всех зонах. Сейчас реализованы HTTP-сводки `cqa.requests` и безопасная диагностика `cqa.errors` (D-009). События импорта, worker, AI и интерфейса ниже добавляются владельцами вместе с соответствующими модулями; их наличие в инструкции не означает готовности этих модулей.

## Какие события записывать

Журнал должен помогать определить, какая операция завершилась, где произошёл сбой и нужен ли повтор. Записывай начало длительной операции, её фактический результат и существенные изменения состояния. Успешное сохранение отмечай после commit транзакции. Не подменяй логами состояние в БД, результат API или сообщение об ошибке в интерфейсе.

| Уровень | Когда использовать |
| --- | --- |
| DEBUG | Временная техническая диагностика с теми же ограничениями данных; по умолчанию выключена |
| INFO | Старт/готовность/остановка сервиса, начало и успешное завершение импорта или оценки, сохранение версии или решения |
| WARNING | Ожидаемый отказ/конфликт/невалидный ввод, временная ошибка с запланированным ограниченным повтором |
| ERROR | Окончательный провал операции, внутренняя ошибка, недоступная БД, прерванный запуск или сбой после начала HTTP-ответа |

Для HTTP действуют уже реализованные уровни: успех INFO, 4xx WARNING, 5xx ERROR. Поздний сбой имеет ERROR и `INTERNAL_ERROR`, даже если заголовки с 200 уже отправлены. Ожидаемое завершение сервиса не является ошибкой.

Имена событий и коды задавай константами разработчика: например, `event=dataset_import_completed`, `error=DATASET_UNAVAILABLE`. Новый публичный код API согласуется по `API_CONTRACT.md`; внутреннее имя события само по себе API не меняет. Не превращай `str(exc)`, текст ответа или пользовательский ввод в код/событие.

## Формат и безопасные данные

Используй стандартный `logging.getLogger("cqa.<module>")` с общей конфигурацией приложения. HTTP-сводки остаются в `cqa.requests`, места внутренних исключений — в `cqa.errors`. Для будущих модулей подходят `cqa.import`, `cqa.worker`, `cqa.evaluation`; не создавай собственные handlers и `basicConfig` в каждом модуле.

В HTTP-сводке допустимы только статус, длительность, число записей при наличии и безопасный код. В отдельном журнале операций можно добавить фиксированное событие, состояние операции, номер фактической попытки и числовые счётчики (`received`, `created`, `new_versions`, `unchanged`). Поля берутся из проверенных технических значений. Не записывай весь объект ради одного счётчика.

Пример для будущего импортера после успешного сохранения:

```python
import logging

logger = logging.getLogger("cqa.import")

# duration_ms и received — проверенные числовые значения операции.
logger.info(
    "event=dataset_import_completed status=completed duration_ms=%d records=%d",
    duration_ms,
    received,
)
```

На любом уровне, включая DEBUG, исключи:

- `.env`, ключи, авторизацию, cookies, полные настройки и переменные окружения;
- URL, query string/`sig`, аудиоссылки и внешние идентификаторы организаторов;
- тексты/массивы сообщений, промпты, ответы модели и исходные HTTP/SQL payload;
- `str/repr(exc)`, `logger.exception`, `exc_info`, полный traceback, исходные строки и локальные переменные;
- полный объект frontend `Error`, `Request`, `Response` или API payload в браузерной консоли.

Не включай SQLAlchemy `echo`, подробный сетевой/SDK debug или обычный access-log с URL. Сохрани текущий запуск uvicorn с `--no-access-log`. В CLI логи идут в stderr, чтобы не повреждать машинный JSON/CSV в stdout; сырые приватные данные и диагностические файлы остаются в игнорируемых каталогах.

## Как обрабатывать ошибку

1. Выбери фиксированный безопасный код и корректное поведение: безопасный ответ, сохранённый `failed` или ограниченный повтор.
2. В HTTP-обработчике используй `error_response(..., request=request)`: middleware добавит одну сводку с этим кодом. Обычные 4xx не требуют дополнительного traceback.
3. Если граница обрабатывает внутреннее исключение, вызови `log_internal_error("FIXED_CODE", exc)` из `app.diagnostics`. Помощник пишет только код и до 16 мест `файл:строка` внутри репозитория; не форматирует текст исключения, включая цепочки и группы.
4. Если исключение передаётся выше без обработки, оставь диагностику принимающей границе. Одна ошибка не должна создавать одинаковые записи на каждом уровне вызовов. Отдельная HTTP-сводка и одна запись диагностики допустимы.
5. Worker/CLI самостоятельно журналируют провал и сохраняют нужное состояние: они работают за пределами HTTP middleware. Каждая фактическая повторная попытка может иметь WARNING с номером и безопасным кодом; окончательный отказ — ERROR. Не скрывай бесконечные повторы за логами.

## Что добавляет каждый участник

| Участник | События в своей реализации | Особые ограничения |
| --- | --- | --- |
| Абулхаир | Готовность/остановка сервера, health/БД, общая обработка ошибок, диагностика запуска и CI | Сохраняет общую конфигурацию, безопасные HTTP-сводки и видимость ERROR; не печатает окружение/секреты в CI |
| Чингиз | Результат импорта с числовой сводкой; переходы worker; успешное сохранение версии чек-листа/решения апелляции; сбои БД | Пишет успех после commit, worker отдельно обрабатывает провал; не выводит записи импорта или SQL-параметры |
| Нурсултан | Начало/результат AI-оценки; фактические попытки, таймауты/отказы/ошибки структуры и доказательств; итог benchmark в агрегатах | Использует безопасные коды; не выводит промпт, ответ модели и транскрипт; чистые функции расчёта не спамят журналом |
| Артём | Существенные сбои загрузки/импорта/оценки/сохранения/апелляции в общем API-клиенте и обработчиках UI | В консоли только фиксированное событие, статус и безопасный код; пользователь видит понятную ошибку, render/polling не создают отдельный поток событий |

Это дополняет текущие задачи участников, не передаёт владение их кодом интегратору и не требует отдельной системы сбора логов. Новые зависимости, удалённая телеметрия и внешний сервис мониторинга для выполнения этой инструкции не нужны.

## Проверка и передача

Для существенного нового отказа воспроизведи его на собственных синтетических данных. Убедись, что есть ожидаемый код и уровень, нет дублирования диагностики и секретных маркеров. На backend используй `caplog`; для интерфейса проверяй консоль в соответствующем браузерном сценарии. Отдельно проверь результат операции: отказ не становится успехом, исходная история сохраняется, число попыток ограничено. Для изменений общего логирования сохраняй проверки CORS, preflight, поздних ошибок и видимости ERROR при `CQA_LOG_LEVEL=ERROR`.

В результате задачи/PR укажи журнал и события, короткие шаги воспроизведения и фактическую команду проверки. Не прикладывай необработанный приватный журнал. Обнови роадмап вместе с реализацией; существенную смену общего подхода сначала зафиксируй в `DECISIONS.md`.

Логи приложения видны в терминале. Сохранение локального файла и просмотр контейнера описаны в [README](../README.md#логи-для-диагностики). `artifacts/` и `*.log` игнорируются Git; файлы журналов в коммит не включаются.

## Пакетная оценка и сдача (A-19)

Backend использует `cqa.batches`: INFO `evaluation_batch_saved records=N` только
после commit. `cqa.submissions`: INFO `submission_export_completed records=N failed=N`
после успешного завершения операции; WARNING `submission_export_rejected` с
фиксированными `SUBMISSION_CHECKLIST_INCOMPATIBLE`/`SUBMISSION_DUPLICATE_CONVERSATION_ID`,
либо `submission_result_rejected error=SUBMISSION_INVALID_RESULT records=N`.
Сами evaluations/worker сохраняют текущие события; отдельный HTTP/polling лог не
добавляется. Успешный экспорт означает корректное формирование файла, не точность AI.

Frontend передаёт только фиксированное событие, HTTP-статус и разрешённый safe code.
Название команды, batch/request IDs, фильтры, payload экспорта, explanation и ошибки
провайдера в консоль не попадают. Offline intake использует `cqa.benchmark`;
в журнале только результат/счётчики и фиксированный код, без путей, case IDs,
имён аудиторов и содержимого human labels. Сценарии проверки: no-key batch503,
частичный failed, конфликт request_id, несовместимый экспорт и невалидный human draft.

## Полнота сдачи и денежный учёт (A-21, D-027)

`cqa.submissions` дополняется WARNING `submission_export_rejected` с фиксированным
`SUBMISSION_SCOPE_MISMATCH` и числовыми `records/missing/extra`. Сами expected/actual ID
не выводятся. Preflight использует одну обычную HTTP-сводку; отдельного журнала
чтения файла или polling нет. Filename, reference JSON и название команды не логируются.

`cqa.budget` записывает INFO `ai_budget_initialized` с числом восстановленных резервов,
`ai_budget_reserved`, `ai_budget_waiting` (однократно за ожидание) и `ai_budget_settled`
для известного учёта. Неизвестный исход даёт WARNING `ai_budget_settled status=unknown`;
отказ — WARNING `ai_budget_rejected` с фиксированным финансовым кодом. Сбой БД —
ERROR `ai_budget_failed error=AI_BUDGET_UNAVAILABLE` и одна безопасная диагностика
`cqa.errors`. Не выводятся суммы/настройки, evaluation/reservation IDs или SQL payload.

Provider сохраняет `cqa.evaluation`: `ai_budget_rejected`, `ai_budget_retained` и
`ai_request_interrupted` дополняют события фактических попыток. Ожидание резерва и
локальный отказ до SDK не увеличивают `request_count`. Сценарии регрессии: нулевой
лимит, неизвестная policy, недостаток/временная занятость квоты, таймаут/отмена с
сохранением unknown, ошибка БД, несовпадение reference. Проверяются безопасный код,
уровень, отсутствие синтетических секретных маркеров и сохранность учёта/истории.
