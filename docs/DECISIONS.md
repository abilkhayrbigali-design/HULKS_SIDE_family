# Решения и история изменений плана

Дата начального плана: 2026-11-07. Это предлагаемые решения команды в рамках известных требований, а не дополнительные правила организаторов.

## D-001. Облачная модель за заменяемым интерфейсом

Историческое решение исходного проекта. Стартовая модель текущей рабочей копии
уточнена прямым выбором пользователя в D-013; интерфейс провайдера сохраняется.

**Решение:** начать с OpenAI Responses API и Structured Outputs; имя модели брать из настройки. GPT-6 Astra — начальный кандидат. Провайдер подключается через внутренний интерфейс, чтобы можно было сменить модель или позднее добавить локальную.

**Причина:** за 24 часа основной ресурс направляется на точность и законченный рабочий процесс. Требование показать локальную и облачную архитектуру одновременно отсутствует.

**Проверка решения:** сравнить оценки с ручной разметкой на RU/KZ/EN, записать стоимость, задержку и ошибки. Изменить выбор, если проверка показывает преимущество другого доступного варианта. Не объявлять качество на казахском подтверждённым до этой проверки.

## D-002. React/Vite, FastAPI, SQLite

**Решение:** отдельный клиент React/TypeScript/Vite и API на FastAPI. SQLAlchemy + Alembic, SQLite и один серверный процесс. PostgreSQL — возможная последующая миграция, а не часть обязательного MVP.

**Причина:** понятное разделение работы четырёх участников и небольшая инфраструктура. Клиент собирается в HTML/CSS/JavaScript; интеграция с Dynamics 365 остаётся будущей задачей, а не обещанием готового компонента.

**Ограничение:** несколько API workers с независимыми очередями не поддерживаются этим планом. До масштабирования нужен пересмотр планировщика задач и хранения.

## D-003. AI оценивает критерии, код считает итог

**Решение:** модель возвращает применимость, ответ, объяснение и ссылки на сообщения. Сервер валидирует их и считает результат через Decimal по формуле из чек-листа. Грубые нарушения — отдельный флаг.

**Причина:** исключить случайные арифметические ошибки и обеспечить воспроизводимый пересчёт после изменения человеческого решения.

## D-004. Неизменяемые версии и история

**Решение:** оценка ссылается на конкретные версии транскрипта и чек-листа. Изменение чек-листа создаёт новую версию; повторная оценка создаёт новый запуск. Апелляция сохраняет исходный ответ и добавляет отдельное решение.

**Причина:** можно объяснить, какие правила применялись, и показать исходный и финальный результат.

## D-005. Живой роадмап

**Решение:** каждый агент обязан обновлять `docs/ROADMAP.md` при изменении статуса, зависимостей и необходимой работы. Существенная смена плана фиксируется здесь с причиной и затронутыми задачами.

**Причина:** дальнейшая работа других AI должна опираться на актуальный план, а не на неизменяемый список предположений.

## D-006. Разметка и метрики команды

**Решение:** создать ручную разметку части DEV и отдельную от настройки промптов отложенную выборку. Внутренние метрики: совпадение по критериям, ошибка итогового балла, качество N/A и флагов нарушений, с разбивкой по языкам.

**Причина:** в DEV API нет Ground Truth. Официальная формула сравнения скрытого набора неизвестна; нельзя выдавать наши метрики или самооценку модели за официальный результат.

## D-007. Исполняемый общий контракт и граница стартового каркаса

**Решение:** A-02 ведёт независимый от реализации источник `contracts/definitions.py`, экспорт OpenAPI 3.1 и JSON Schema внутреннего ProviderResult, а также собственные синтетические примеры. Чингиз реализует Pydantic/маршруты в своей зоне, Нурсултан — провайдер/проверки/расчёт, Артём — клиент. Общие схемы не являются реализацией этих модулей или схемой Structured Outputs для прямой отправки модели: адаптер провайдера должен учитывать поддерживаемое API подмножество JSON Schema.

**Уточнение контракта:** фиксируются ранее нерасписанные поля `latest_evaluation`, `usage`, содержимое карточки апелляции/решения, nullable provenance до вызова, пагинация чек-листов и source=`dataset|upload`. Результат решения содержит полный фактически принятый ответ, включая confirm. Неизменяемость и арифметику по-прежнему проверяют сервисы и тесты C/N; JSON Schema проверяет структуру.

**Стартовый каркас:** `app.main.create_app` владеет lifespan и `app.state.engine`, `app.state.settings`; C-01 использует этот engine или согласует замену. Настройки загружают корневой `.env`, относительный SQLite-путь считается от корня репозитория. Health действительно выполняет `SELECT 1`; таблицы/seed появляются только в C-01. До C-02 отсутствуют бизнес-маршруты, успешные AI-ответы не эмулируются. `require_llm`/`require_dataset` дают безопасные 503 при вызове из сервисов. Стартовые CI и `compose.api.yaml` проверяют только backend; полный Compose/worker и клиент остаются в A-03/A-04/R-01.

**Причина:** дать коллегам воспроизводимую базу, не переписывая их зоны. Полный A-01 требует R-01; окончательное согласование A-02 подтверждается совместимостью реализаций C/N/R, а не только наличием экспортированного файла.

## D-008. Безопасная проверка URL и граница обработки HTTP-ошибок

**Решение:** общая проверка HTTP URL проверяет порт и пробельные символы, не изменяя исходный подписанный URL. Валидаторы настроек заменяют ошибки парсера безопасным сообщением. SQLite URL с credentials или портом отклоняется до создания engine.

Обработку безопасных ошибок и журнал запросов перенести с `BaseHTTPMiddleware` на ASGI middleware: граница охватывает отправку тела и фоновые задачи ответа. До отправки заголовков ошибка даёт прежний безопасный JSON 500; после начала ответа статус уже нельзя заменить, поэтому исключение подменяется безопасным без исходного контекста и журналируется код `INTERNAL_ERROR`. CORS остаётся снаружи. Форматы и маршруты API не меняются.

**Причина:** регрессии A-08 подтвердили, что прежняя проверка пропускала нерабочие настройки, ошибки `urlsplit` раскрывали часть входного значения, а исключения после `call_next` могли попадать в traceback сервера с подписанным URL.

## D-009. Диагностика ошибок без приватных значений

**Решение:** разделить защиту от исходных исключений и журнал запросов. Порядок middleware снаружи внутрь: журнал → CORS → безопасная обработка исключений. Это сохраняет CORS на безопасном 500 и включает preflight в журнал. Один запрос даёт одну запись `cqa.requests`: только статус, длительность и безопасный код; уровни INFO для успеха, WARNING для 4xx и ERROR для 5xx или сбоя после начала ответа. Код обработанной ошибки хранится в ASGI scope конкретного запроса, без служебного заголовка ответа.

Для внутренних исключений и недоступной БД отдельный `cqa.errors` пишет безопасный код и ограниченный список мест в коде репозитория (`файл:строка`). Тексты исключений/групп/причин, исходные строки Python, локальные переменные, URL и содержимое запроса не записываются. Полные traceback/`logger.exception` для этих ошибок не используются. Следующие сервисы могут переиспользовать этот помощник; прикладной JSON и API остаются прежними.

HTTP URL дополнительно отклоняет управляющие символы; URL набора данных — разделитель `#`, поскольку fragment не передаётся серверу. Подписанный URL с корректным percent-encoding сохраняется без изменения.

**Причина:** A-09 воспроизвела восемь случаев принятия некорректной настройки и девять случаев отсутствующей/неинформативной диагностики. Пользователь отдельно поручил добавить безопасные логи для последующих агентов.

## D-010. Независимая проверка работы Нурсултана перед main

Область действия этого первоначального решения расширена D-012: теперь процедура обязательна для всех участников и реализующих агентов.

**Решение:** по прямому указанию пользователя перед слиянием каждого PR Нурсултана запускается отдельный агент на `gpt-6.1-sol` с уровнем рассуждения `xhigh` (Extra high). Он проверяет изменения относительно актуального main: ошибки, расчёты и контракты, логирование, тесты, дублирование и лишний код. Порядок и задание reviewer — в `CODE_REVIEW.md`.

**Условия слияния:** отчёт относится к точному head SHA, подтверждённые замечания исправлены, проверки пройдены, изменённый код повторно просмотрен. Reviewer сам не меняет код и не сливает PR; это сохраняет независимость проверки. Отчёт AI не заменяет CI и интеграционную проверку.

**Граница:** это обязательное условие для работы Нурсултана. Остальным участникам такой дополнительный агент назначается отдельным поручением. Сейчас фиксируется процедура; код N-01/N-02 и его фактическое ревью ещё не готовы.

**Модель:** пользователь назвал Sol Extra high; конкретизировано до доступной модели GPT-6.1 Sol и `xhigh`. [Официальная документация модели](https://developers.openai.com/api/docs/models/gpt-6.1-sol) подтверждает этот уровень. При недоступности нужной модели нельзя молча объявлять проверку другой моделью выполнением требования.

## D-011. Завершение записи до HTTP-ответа и общие ошибки данных

**Решение:** зависимость сессии завершается в scope `function`: commit выполняется до отправки успешного ответа. События сохранения публикуются только после commit, при rollback отбрасываются. `install_data_api` использует общий `app.main.error_response`; диагностика — `app.diagnostics.log_internal_error`. После синхронизации с текущим main в C-07 временные локальные fallback-обработчики удалены.

**Причина:** ревью C-06 выявило возможность ответа 200 при ошибке commit и отсутствие журналов операций. Публичные маршруты и поля API не меняются; каркас в C-07 перенесён из origin/main без правок чужой реализации.

**История ID:** решение о commit до HTTP-ответа первоначально имело ID D-010 в codex/chingiz. При объединении с main в C-08 оно получило D-011, чтобы сохранить уже опубликованный в main D-010 о проверке Нурсултана. Содержание обоих решений сохранено.

## D-012. Обязательное независимое ревью для всей команды

**Решение:** пользователь расширил D-010 на всех участников и AI-агентов. Перед слиянием любого PR в main автор создаёт отдельного reviewer на `gpt-6.1-sol` с `reasoning_effort=xhigh`; проверяются ошибки, логи, контракты, тесты и избыточность в пределах изменённой области. Это относится также к документации, конфигурации и инфраструктуре. Правки выполняет автор, reviewer подтверждает финальные base/head SHA, интегратор проверяет отчёт и CI перед слиянием.

**Организация:** общая повторяемая проверка Q-01 заменяет частную N-06, история N-06 сохраняется как SUPERSEDED. Каждый из четырёх блоков заданий содержит одинаковое требование и ссылку на CODE_REVIEW.md. Проверки выбираются по содержимому PR: документационная правка не требует выдумывать или повторять несвязанные runtime-проверки.

**Граница независимости:** reviewer не меняет отслеживаемые файлы и не запускает reviewer для собственного отчёта. Один отдельный reviewer проверяет PR автора; цепочка рекурсивных проверяющих не требуется. Правило применяется и к PR, который вводит эту общую процедуру. Это правило работы команды; автоматическая защита ветки GitHub этим изменением не настраивается.

## D-013. Изолированная рабочая копия, GPT-6 Luna и проверка без живых вызовов

**Решение:** по поручению пользователя снимок `67a04050936b2c8a36c8bdc865890d29a1d0608c`
перенесён в HULKS_SIDE_family. Исходный HULK-S_FAMILY_REPO доступен строго для чтения;
никаких записей, веток, PR или push туда. Единственный origin у рабочей копии указывает
на HULKS_SIDE_family. Четыре основных агента работают в отдельных рабочих копиях
и наследуют модель/уровень рассуждения родительского агента.

**AI:** пользователь выбрал OpenAI GPT-6 Luna как предполагаемую модель приложения.
Официальный ID `gpt-6-luna`, Responses API и Structured Outputs проверены по
[официальной документации](https://developers.openai.com/api/docs/models/gpt-6-luna).
Модель остаётся настраиваемой через OPENAI_MODEL. Выбор модели приложения
не меняет отдельного reviewer Sol/xhigh по Q-01.

**Проверки:** пользователь явно выбрал текущую работу без живых вызовов OpenAI.
SDK и pipeline проверяются только внедряемыми клиентами/синтетическими ответами.
Без ключа продукт возвращает AI_NOT_CONFIGURED. Живой доступ, стоимость и точность
на человеческой разметке этим не подтверждаются.

## D-014. Сборка приложения и проверка без живых AI-вызовов

**Решение:** `create_app` подключает data/evaluation API; lifespan создаёт один SQLite engine, применяет Alembic на его connection, создаёт session factory и идемпотентный исходный чек-лист, затем запускает внутрипроцессный worker. При остановке worker освобождается до engine. Для :memory: используется уникальная named shared-memory SQLite, отдельные соединения QueuePool и keeper на срок lifespan: polling worker не может зафиксировать чужую транзакцию. Прикладные startup/shutdown ошибки имеют фиксированные безопасные коды; ключ не нужен для готовности API. Сохранённые `queued/running` обрабатывает worker по D-001—D-007, Startup не делает проверочный вызов AI; сохранённые queued начинают обрабатываться после запуска worker по обычным правилам и могут обращаться к AI при настроенном ключе.

**Интерфейс:** Vite собирает `frontend/dist`; FastAPI отдаёт только `/` и `/assets`. Hash-навигация клиента не требует catch-all, который мог бы перехватить 404/405 API. Docker target `api` содержит backend и Alembic; target `app` добавляет собранный frontend. `compose.yaml` запускает один процесс/один volume; `compose.api.yaml` остаётся для отдельного backend.

**Проверка:** offline smoke запускает сервер с новой временной БД и принудительно пустыми `OPENAI_API_KEY`/`CQA_DATASET_API_URL`, проверяет импорт, чтение, исходный чек-лист и `AI_NOT_CONFIGURED` без созданной оценки. Интеграционные тесты проверяют реальные ответы по общим JSON Schema. Моки провайдера предназначены только для тестов, не включаются в пользовательский рабочий режим. A-03/N-04 с реальными оценками остаются невыполненными до разрешения пользователя на живые вызовы и наличия экспертной разметки.

**Настройки:** `OPENAI_MODEL=gpt-6-luna`; `CQA_LLM_MAX_OUTPUT_TOKENS=12000`; `CQA_LLM_REASONING_EFFORT=medium` (low/medium/high). SDK импортируется перед настройкой логов, чтобы поздний import с OPENAI_LOG=debug не включал payload-логирование. Подробные HTTP/OpenAI/SQL логи отключены даже при DEBUG приложения. Значения настроек, URL и payload не попадают в startup-диагностику.

## D-015. SQL-free AI boundary and bounded visible attempts

**Решение:** `EvaluationPipeline.evaluate(*, transcript, checklist)` принимает неизменяемые
снимки как словари либо Pydantic-модели и возвращает `PipelineResult` с `assessment`,
`provenance`, `review_required`, `review_reasons`. SQL и сохранение состояний остаются в C.
`calculate_assessment(*, criteria, results, messages)` повторно используется апелляциями.
Ошибки `EvaluationError` содержат только фиксированные `code`/`safe_message` и известный
`provenance`, без исходного HTTP исключения. `aclose()` закрывает принадлежащий provider клиент.

**Повторы:** Responses SDK работает с `max_retries=0`; один адаптер ограничивает все
сетевые и структурные повторы числом `1 + CQA_LLM_MAX_RETRIES`. Каждый вызов учитывается
в usage, включая невалидные/неполные ответы; неизвестный счётчик любой попытки делает
соответствующий агрегат `null`. Стоимость остаётся `null` без подтверждённого расчёта.
Refusal и ошибки доступа не повторяются. При отсутствии ключа вызова нет и успех не создаётся.

**Доказательства:** проверяются ссылки и порядок диапазонов внутри снимка. Любая роль
допустима как контекст (системное сообщение может подтвердить идентификацию), но модель
получает явное правило оценивать только действия оператора. Валидный JSON и корректные
ссылки не доказывают смысловую точность или устойчивость к prompt injection.

**Ограничение проверки:** пользователь запретил живые OpenAI вызовы на этом этапе.
SDK сериализация и ошибки проверяются только через локальный `MockTransport`; настоящая
доступность модели и качество RU/KZ/EN остаются непроверенными. Человеческий GT не создаётся
моделью: offline benchmark принимает внешнюю ручную разметку с фиксированным holdout.

## D-016 — Сохранённые evaluation и граница worker/апелляций

Дата: 2026-11-07. Ответственный: Чингиз.

`POST /evaluations` фиксирует текущую версию транскрипта и явно выбранную версию
чек-листа. Без ключа возвращается 503 `AI_NOT_CONFIGURED` до создания запуска.
Тесты внедряют Python-объект `app.state.evaluation_pipeline`; HTTP/настройки
не позволяют включить такой режим продукта.

Worker ограничен `evaluation_concurrency`: короткая транзакция claim/load →
`await pipeline.evaluate(transcript=dict, checklist=dict)` при закрытой Session →
короткая транзакция complete/fail. `PipelineResult` содержит assessment, provenance,
review_required и review_reasons. `EvaluationError` содержит фиксированный code,
safe_message и nullable provenance; известный usage сохраняется даже при ошибке.
Отмена provider передаёт per-call aggregate provenance через CancelledError.provenance;
worker сохраняет его вместе с INTERRUPTED. Отменённая попытка с неизвестным usage
не выдаётся за нулевое потребление.
`queued` после старта обрабатывается; прежний `running` становится failed/INTERRUPTED
без повторного платного запроса. Остановка отменяет текущие задачи и закрывает
только принадлежащий приложению pipeline/provider.

SQLite защищает snapshots/оригинальные criterion_results и appeal_decisions
триггерами. Решения выполняются в короткой BEGIN IMMEDIATE транзакции: проверка
revision, immutable decision, final через `calculate_assessment`, revision+1,

## D-024. сохранённые пакеты и официальный экспорт
